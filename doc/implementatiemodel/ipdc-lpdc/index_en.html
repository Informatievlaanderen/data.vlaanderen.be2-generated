Dependencies

This document describes an implementation model, in this case IPDC - LPDC (Deployment Model). This implementation model answers the question of how the corresponding domain model can be applied in practice. It explains the constraints (cardinality, code lists) and lists the corresponding (RDF) terms.

Summary

This implementation model is an implementation model of the ICEG application profile public service and follows the OSLO Vocabulary 'Service'. Many things are taken from the ICEG model and are therefore only described in English. Specific extensions within this data model are described in Dutch.

This implementation model is used to exchange data on public services between IPDC (version 3) and LPDC. It describes how to communicate to and from the local product and service catalogue (LPDC) and the inter-administrative product and service catalogue (IPDC).

Multilingualism

All translatable fields have the type TaalString. A TaalString is the combination of a textual value with an indication of the language. The designation of the language is made on the basis of a language tag. The standard language tags that are supported in this deployment model are the following. Please note that new language tags may be supported in due course.

  • en: Dutch (required)
  • English(optional)
  • fr: French (optional)
  • the: German (optional)

In the implementation model, the cardinalities for TaalStrings are always indicated from a single language. For example, cardinality 1 indicates that exactly 1 textual value is allowed per language. Cardinality 0..1 indicates that there is a no or one value is allowed. The exceptional cardinality 0..* indicates that there are several values per language are allowed.

Formal (you) versus informal (you)

To be able to distinguish between formal texts (u form) and informal texts for Dutch texts (your form) some private use language subtags were agreed.

  • en-BE-x-formal: formal text manually entered by an editor
  • en-BE-x-informal: informal text manually entered by an editor
  • en-BE-x-generated-formal: automatically generated formal text
  • en-BE-x-generated-informal: automatically generated informal text
When writing to IPDC or LPDC, or when submitting changes via LDES, only one of the following language tags may be passed: nl-BE-x-formal, nl-BE-x-informal or nl. Preferably, nl-BE-x-formal or nl-BE-x-informal. In this way, it is clear in which form the editor wrote the original text. When writing to the IPDC or LPDC, the generated tags nl-BE-x-generated-formal and nl-BE-x-generated-informal are not allowed. These will be ignored.
When reading IPDC, the nl tag will always be present. In addition, either the formal form (nl-BE-x-formal) or generated formal form (nl-BE-x-generated-formal) will always be available. As well as the informal form (nl-BE-x-informal) or generated informal form (nl-BE-x-generated-informal) by an editor.

English

Organisations with the YourEurope publication channel are made available on the YourEurope portal. In order to make these instances as findable as possible with a minimum of editing work, these YourEurope instances are automatically translated into English. Automatic translated English texts are displayed in the model by the following private use language subtag

  • en-x-generated: automatically generated English text

Snapshots

A snapshot shows what an instance or concept looked like at a certain point in time. Every time a functional change is made, a new snapshot will be created who captures all attributes and associations filled in at that time. In this way, the complete editorial history of an instance or concept is recorded. To keep the diagram clear, the attributes and associations of instances and concepts are not repeated on the snapshot classes. In the detailed description of these classes, all attributes and associations can be found.

Authority

Description
Institutions are the actual interpretation of a product or service. The competent authority can vary: federal, Flemish, provincial,... And the service can be provided by another government such as a local government. A government service is a mandatory or optional set of activities that are or may be carried out by or on behalf of a public organisation, publicly funded and arising from public policy. Services may benefit an individual, an organisation or association, a company or other public authority, or groups of any of these parties. A service exists regardless of whether it is used or not. According to the revised European Interoperability Framework, a European public service includes any service provided by public authorities in Europe, or by other organisations on their behalf, to businesses, citizens or other public authorities.

Concept

Description
The services provided by local authorities are often based on Flemish, federal or European legislation, which is translated to a local level. This means that the basis is the same for every local government, but that there may be flexibility for the local interpretation. Because we want to get and keep IPDC well stocked and up to date, with a limited administrative burden, we provide the concept. A draft is a template that editors of the Flemish government prepare for local authorities. It contains a general interpretation of a government service, which can also be applicable in most local contexts. Local authorities can consult these concepts and decide to register their own services on the basis of a concept. At that moment, a concept is cloned to an authority. The local government can then fully adapt this body and tailor it to the local context. In this way, a concept also groups together all the different local variations of a similar service.
Usage
A good example of a concept is marriage. Although the description and conditions of a marriage are largely the same for the different municipalities, there may still be local differences, such as the location and price, which can be found in the respective authorities.

Condition

Description
A normal requirement is an atomic requirement. Some criteria can be expressed with several atomic requirements. A normal requirement can specify the expected value that the requirement response has to contain, or a range of threshold values within which the requirement response has to fit in. The normal requirement may apply to a certain period of time. It also can provide a list of candidate evidences that the responder can use to prove the normal requirement.
Usage
Not all public services are needed or usable by everyone. For example, the visa service operated by European countries is not needed by European citizens but is needed by some citizens from elsewhere, or public services offering unemployment benefits and grants are targeting specific societal groups. This model reuses the Core Criterion and Core Evidence Vocabulary for this class. The CCCEV provides more details but the Requirement class has three mandatory properties.

Contact details

Description
This class represents the contact information for a Public Service, Channel, Public Organization, etc. It is defined in the Core Public Organization Vocabulary and is provided as a schema:ContactPoint. Like Channel, a Contact Point may have regular opening hours that are then overridden by, for example, public holidays, using the Opening Hours Specification class.
Usage
At least one of the attributes must be filled in with a non-empty value.
Properties
The following properties are defined for this entity: Address , Email , Opening hours , Order , Phone number , URL .
Property Expected Type Cardinality Description Usage Codelist

Opening hours String 0..1 The value of this property is structured text that gives the hours at which the contact point is normally available. Days are specified using two-letter combinations: Mo, Tu, We, Th, Fr, Sa, Su. If the Contact Point is only available on Tuesday and Thursday between 6 and 8pm, the value would be Tu,Th 16:00-20:00.

Description
An instance snapshot shows what an instance looked like at a particular point in time. Each time a functional change is made, a new instance snapshot will be created. In this way, the complete editorial history of an instance is recorded.
Usage

Procedure

Description
The Rule class represents a document that sets out the specific rules, guidelines or procedures that the Public Service follows. It includes the terms of service, licence, and authentication requirements of the Public Service. Instances of the Rule class are FRBR (Functional Requirements for Bibliographic Records) Expressions, that is, a concrete expression such as a document, of the more abstract concept of the rules themselves. This model does not envisage instances of the Rule class as machine-readable business rules. Detailed modelling of the rules related to Public Services is out of scope of this model.

PublicOrganization

Description
An organisation that belongs to the public sector according to a legal framework, regardless of the level of government at which that framework is in force.
Usage
Link to the organisation register (guide) based on the OVO code or link to the organisation portal. Where possible, IPDC tries to establish links to the organization register. When IPDC receives a link to the organisation portal, it tries to look up the organisation in the organisation register. When this is found, the link to the organization register will be saved, otherwise the link to the organization portal will be retained.

No properties are defined for this entity.
